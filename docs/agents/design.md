# Approved product design

Read this before changing layout, motion, gestures, sheets, swipes, reordering,
navigation-detail behavior, or any other interaction contract.

`AGENTS.md` owns the standing rule against replacing the visual language. This
file owns the palette, the reference viewports, and the interaction contracts
built on them.

## References, viewports, and palette

The approved visual references are stored in `docs/design/`:

- `budget-responsive.png`: primary budget and responsive layout.
- `brand-system.png`: wordmark and app icon.
- `transactions.png`: transaction list, editing, and split flows.
- `auth-income-organizer.png`: sign-in, income, month copying, and organization.

Important responsive reference viewports are 390 x 844 for mobile and
1440 x 1000 for desktop.

The visual system is deliberately iOS-like and restrained: true-white surfaces,
charcoal text, and cool-gray dividers; cornflower blue `#1769E0` as the primary
action color; and mint `#55D49B`, sky `#9FC0FF`, yellow `#FFD977`, coral
`#FF7E83`, and lilac `#B6A6FF` as semantic accents. Pastel category medallions,
tactile sheets, rounded cards, lightweight CSS/SVG charts, a mobile bottom
navigation, and bottom-sheet interactions carry the rest. Desktop uses a slim
left navigation, a primary budget column, and a summary/activity rail.
Interactive targets are at least 44 px, with safe-area padding, keyboard focus
management, accessible status announcements, and reduced-motion support.

## Interaction contracts

- Category headers expose an edit menu; budget-item rows alone use a deliberately leftward swipe to reveal Delete. Keep the inactive swipe action fully transparent so fast vertical scrolling cannot flash its red layer.
- The Budget page defaults its amount display to Available unless the per-device Settings preference selects Planned. Switching Planned/Available on the Budget page remains temporary and must not resize rows. A line-item progress bar represents the share of its starting available balance still remaining: it is full before any net spending and shrinks toward empty as spending consumes the balance, including carried-in funds and refunds. A negative balance replaces the regular fill with a coral striped warning bar and an accessible over-budget amount. Reordering starts after a 350 ms long-press on the category header or item row; movement beyond 8 px before activation must cancel so vertical scrolling and item swipe-delete remain reliable. A visually hidden keyboard control must continue to support Arrow Up/Arrow Down reordering. Use a transition-free rendered drag copy inside a neutral compositor shell plus animated list reflow. Never move the source clone directly with inherited row/header transitions because that creates compositor ghosting. During a pointer drag, keep the real DOM order fixed, translate the faded placeholder into the current target slot, and move neighboring rows with interruptible transforms; commit the React/server order once on drop. Edge auto-scroll is frame-based with gradual acceleration/deceleration and continues while the pointer is held near an edge. Item reordering remains within its current category. Summary and budget progress entrance animations are one-shot and must not replay when a drag preview is created or a list order is committed.
- Budget-item details are URL-backed and use an iOS-style navigation push below 760 px. The detail page slides in from the right while the mobile header, Budget content, and bottom navigation parallax left; Back, browser history, refresh, and an app-controlled left-edge swipe all preserve navigation-stack semantics. The global left-edge guard must leave this custom swipe available from x=0 while suppressing Safari's cancelable native history gesture. Disable the underlying detail swipe while any child sheet is visible or exiting so add/edit transaction interactions cannot pop the line-item route. Keep the Budget back control and editable item title in a fixed detail header while only the detail body scrolls, led by a prominent remaining-this-month summary. A floating blue plus action remains at the bottom right and opens the add-transaction sheet with the current item preselected. Item-scoped add and edit transaction sheets are full-screen below 760 px, omit the mobile close control and grabber, and retain the header Add/Save action; at 760 px and above, they use the shared centered modal treatment. Global transaction sheets retain their established standard presentation. The push, pop, and edge-swipe motion is ported from the Cinalysis push stack and reads from the `--navigation-detail-*` tokens in `tokens.css`: a push moves the detail and the Budget layer together over 0.5 s on the push curve `cubic-bezier(0.3, 0.84, 0.21, 1)`, the Budget layer parallaxing a fixed 128 px left; Back reverses both layers together on that same duration and curve; Cinalysis returned the underlying layer over 0.65 s on its softer return curve, which left the Budget layer visibly trailing the detail and was dropped. Neither direction delays either layer: Cinalysis's 0.1 s start delay made the two layers start out of step and read as a stutter on device, so it was removed. Its job — giving the freshly mounted detail time to render before it moves — is done instead by holding the entrance: the detail mounts with its entrance animation paused off-screen, and `NavigationDetail` sets `data-navigation-detail-state='open'` on the body only after two animation frames, which starts the detail's animation and the Budget layer's parallax on the same frame. Without that hold, the slide began on the frame the detail first rendered and showed it half-painted. The edge swipe writes each pointer event's position straight to inline `transform`s on the detail and on `.app-frame`, with transitions off while the finger is down, so the detail tracks the finger 1:1 at the touch-event rate (60 Hz on iOS Safari, which also caps `requestAnimationFrame` at 60 Hz). That cap is Safari's, not the code's: turning off the Safari feature flag "Prefer Page Rendering Updates near 60fps" (Settings → Apps → Safari → Advanced → Feature Flags) makes the same drag track at 120 Hz on a ProMotion iPhone, confirmed on device. Only a native scroll could get past the cap without the flag, and that rebuild has not been pursued. This replaced Cinalysis's two script smoothing stages (an input filter plus a rAF frame driver), which trailed the finger by about 45 ms. Do not interpolate the drag with a short CSS transition retargeted on every event: on device it made the drag stutter, and when a flick ended the last follow transition's `transitionend` fired during the exit and completed the dismissal early, closing the detail twice. Drag frames must never write custom properties on `body`: custom properties inherit, so a per-frame write there restyled the whole document every frame; writing `transform` on the two composited layers touches only those elements. Settling and dismissing switch the state attributes, force a reflow, and only then write the target transforms, so the transitions start from the dragged position. The drag measures from the point where it claims the direction, so activation never jumps, and a re-grab reads the rendered position from the detail's bounding box, which includes an in-flight settle. Release velocity (`releaseVelocity` in `src/components/ui/gesture-release.ts`, shared with sheets, which also owns the exit timing constants) is a least-squares slope over the coalesced samples from the last 80 ms, and is zero when the finger rested more than 60 ms before lifting. A lift-off sample at the last position is not recorded: it would read as a pause and cut a flick's speed. An exponential filter was dropped for the same reason: on a flick of about 80 ms it never reached the finger's speed, so the exit started slower than the finger and looked like a hitch. Release dismisses past 150 px, or on a flick of at least 24 px at 0.55 px/ms. The exit is matched to the finger: its duration is 1.6 times the time the remaining distance takes at the release speed (floored at 0.5 px/ms), clamped to 160–400 ms, and to at most 300 ms for a release at flick speed (0.55 px/ms or faster), and its curve is `cubic-bezier(0.3, y1, 0.21, 1)` with `y1` chosen so the curve's starting slope equals the release speed, clamped to 0.3–1 so it never overshoots. The same `transition` is written inline on both the detail and `.app-frame`, so the Budget layer stays in step. It must not travel through custom properties on `body`: that restyled the whole document on the release frame, which read on device as a pause before the panel shot off. The body's `--navigation-detail-dismiss-duration` is written only once the exit has finished, for the 1 ms close animation. Otherwise the detail settles back over 0.4 s on the return curve `cubic-bezier(0.4, 1, 0.4, 1)` while the Budget layer returns to its parallax over 0.5 s on the push curve. `restingParallax` in `edge-drag.ts` must equal `--navigation-detail-parallax`, and `settleDuration` must equal the longer of the two settle transitions, since it clears the settling attributes.
- The mobile bottom navigation is a floating Liquid Glass-style capsule, inset from the screen edges and lifted above the home indicator, rather than an edge-attached bar. Safari exposes no native glass or backdrop refraction to web content, so the material is layered by hand: a lightly tinted translucent fill, a light `backdrop-filter` blur with saturation so content stays visible through the bar, a top specular sheen, and a light-catching gradient rim stroked along the continuous outline (a masked CSS rim until that outline is measured), with an opaque fallback where `backdrop-filter` is unsupported. The glass lives on its own `.bottom-nav-surface` layer rather than on the nav: the continuous-corner clip-path makes its element a backdrop root, so on the nav itself it would blank the blur. Write only the unprefixed `backdrop-filter` and `mask`: Tailwind's Lightning CSS generates the `-webkit-` forms, and a hand-written prefixed declaration after the standard one replaces it in the output, leaving Chromium with no blur at all. A single glass lens pill marks the active tab and slides between tabs on a spring curve with slight overshoot, squash-stretching as it travels. It must not stretch on first render, only on a tab change. Pressing the active tab swells the lens; tab icons never scale on press. The bar's inner width snaps to a multiple of 4 and its left edge to a whole pixel with CSS `round()`, so every tab edge and lens stop lands on a whole pixel; a half-pixel split lets the lens and tab layers round in different directions, visibly off-center on a phone. Tabs are not link-draggable, and the lens and tabs keep permanent compositing layers (`will-change: transform`) so icons do not re-snap by half a pixel while the lens animates. Reduced motion removes the slide and stretch. The bar and lens use continuous corners (below), and the bar waits offscreen until its shape is measured, then slides up on load; only `transform` animates, because opacity below 1 would make the nav a backdrop root and flash the glass clear. `--bottom-nav-height` is the capsule's full footprint including its bottom offset; content padding, scroll padding, the toast offset, and drag edge auto-scroll all derive from it or from the nav's measured top. WebKit does not clip a `backdrop-filter` to a clip-path, so on iOS the blur painted the plain circular capsule and showed as a light rim past the smoothed ends; the surface therefore also carries a mask of its continuous outline (`continuousMask`), which WebKit does apply to the blur. That mask would cut off a shadow on the surface itself, so the drop shadow lives on a sibling `.bottom-nav-shadow` layer behind it: a plain `box-shadow` inset 1 px, so the shadow starts under the smoothed edge instead of leaving an unshadowed sliver between the edge and the circular shadow, and opted out of the native superellipse, which squared its ends in Chromium. The outline's hairline is a 6 % `ContinuousStroke` drawn along the curve, not a `0 0 0 0.5px` box-shadow ring, which followed the circle and hid the capsule smoothing entirely. Do not draw that shadow with an SVG blur or a `drop-shadow` filter on a filled copy of the outline: iOS Safari clipped the SVG blur to a rectangle, and the filled copy's antialiased edge leaked a dark line along the ends.
- Corners are continuous (curvature-smoothed) with one curve drawn two ways, set by three tokens in `tokens.css`: `--corner-superellipse` (1.8; higher is smoother and squarer), `--corner-extent` (1.55; how far past the authored radius the curve reaches, higher is rounder), and `--capsule-smoothing` (0.3) for pill ends. Apple's own corner is about superellipse 1.38 at extent 1.24, which at this app's sizes is within a fraction of a pixel of a plain circle, so the app deliberately runs more continuous than that. Where the browser draws `corner-shape` natively (Chromium today), one `@supports` rule gives every element the superellipse and sets `--corner-radius-scale` to the extent; every rectangular `border-radius` is therefore authored as `calc(Npx * var(--corner-radius-scale))`, and new ones must be too, while circles (`50%`) and pills (`999px`) stay literal. Elsewhere the scale stays 1 and corners are plain circles. On iOS today, continuous corners come from `src/components/ui/continuous-corners/`: `useContinuousCorners` for the tab bar and lens, the Budget and Income summary cards, and every sheet, and `ContinuousControls`, mounted once in `providers.tsx`, which attaches to every element matching its button selector list (primary and soft buttons, the Expense/Income segmented control and its thumb, filter tabs, the icon, tone, and organizer action buttons, the sheet header submit, the month picker control and its month cells, and the toast action) as they enter the DOM. Add a class to that list when a new button style needs continuous corners. Both apply the same superellipse and extent (their elements keep a scale of 1), or a capsule end when the radius fills a side. The element paints the largest circular radius that contains the curve and its clip-path removes only the slivers between that circle and the curve, so shadows, focus rings, and contents keep painting normally. A CSS border stays and is also stroked along the curve as a background layer, re-read whenever a state attribute, hover, or border transition changes it. That layer is `!important`, because component state rules restyle with the `background` shorthand, which would reset it at any specificity. The border color must be opaque so the two do not double up, and a bordered continuous element must use `background-color` rather than a background image. The mechanics, all in `src/components/ui/continuous-corners/`: `geometry.ts` first mirrors CSS by shrinking radii that overflow a side together by one factor, then scales each by the extent. A corner whose scaled radius fills a whole side becomes a capsule end, whose curvature ramps linearly from zero (a clothoid) through the `--capsule-smoothing` share of its 90° turn along the longer edge and then holds as a circular arc; every other corner is the `superellipse(K)` curve with exponent 2^K, exactly what `corner-shape` draws. `attach.ts` sizes from the ResizeObserver border-box size, which is fractional and ignores transforms: `offsetWidth` rounds, and the half-pixel error was visible at the tab bar's 4 px gaps. `useContinuousCorners` returns a callback ref, so an element that remounts (the lens replays its stretch by remounting) is re-attached, and `ContinuousControls` skips elements a hook already manages. `ContinuousStroke` draws a gradient rim inside the outline for surfaces that have no CSS border, which is how the tab bar and lens get their light-catching edges. A decorative shape attached this way must be a real element, not a pseudo-element, which is why the segmented control's thumb is a `<span>`. The clip applies to the element's whole subtree, so anything overhanging a continuous element's corner must be its sibling, not its child: the Transactions filter count badge sits beside the filter button in a positioned wrapper for that reason. A radius scaled past half an element's side becomes a circle or pill end, and one that nearly reaches it leaves almost no straight edge: a small square control reads as a circle. Keep the authored radius times the extent to about 85% of half the element's shorter side, which is why the 44 px filter button uses 12 px rather than 14 px. Circles and pills keep `corner-shape: round`: add any new one to the opt-out list in `tokens.css`, or the native superellipse will square it off.
- The detail header title collapses with the scroll, never on a timer. The expanded title wraps and is left aligned; as it scales toward the compact bar its wrapped remainder dissolves, the single-line layout takes over at 65 % of the collapse, and the text that line could not show reveals across the remaining scroll so the motion reverses when scrolling back up. Truncate the compact title against its drawn width rather than its laid-out width, keep it centered in the bar, and keep the visible text continuous across the layout swap. Register any custom property used for these fades with `@property`; unregistered custom properties and CSS gradients animate discretely and snap. Where scroll-driven animations are supported, the collapse finishes within `--navigation-detail-collapse-range` (the expanded-minus-compact header height, about 50–65 px) through `animation-range`. The title's `navigation-detail-title-collapse` keyframes animate only registered custom properties: `--navigation-detail-title-progress` from 0 to 1, plus the tail and head fades. The title's `transform` is computed from those properties in `navigation-detail.css` and is never a keyframe property. On iOS Safari a `transform` keyframe on the title ignored the length-based `animation-range`, so the title shrank across the whole list's scroll height while the header background, which animates the non-accelerated `clip-path`, collapsed on time. On a long Organize list the title then needed hundreds of pixels of scroll to collapse. The 65 % keyframe stop and the `0.65` in that transform are `titleRevealProgress` in `title-motion.ts`, and `20 / 46` is its `titleCompactScale`; change them together. Past the stop the head fade equals the reveal fraction, so the transform reuses it for the final horizontal glide. A soft 10 px shadow (`.navigation-detail-header::after`) sits under the white header background's clipped bottom edge. It rises with that edge and fades in with the collapse, from none when expanded to full once compact. The header's `clip-path` would cut off a shadow on the background itself, so it is a separate pseudo-element. For the same Safari reason as the title, its `opacity` and `transform` are computed from the registered `--navigation-detail-header-progress` rather than being keyframed. The scroll-driven path animates that number, and the script fallback writes it on the header beside `--navigation-detail-header-collapse-y`.

The sheet drag follows the same rules as the navigation-detail edge swipe below: each pointer event writes an inline `transform` directly, with no smoothing driver and no per-frame custom properties. Release velocity and the speed-matched exit come from the same helpers in `src/components/ui/gesture-release.ts`, and the exit `transition` is written inline on the sheet. - The mobile PWA intentionally disables page zoom, text selection, touch callouts, document-level pull-to-refresh, and cancelable Safari history gestures beginning within the leftmost 20 px on any route. The global touch guard must remain capture-phase and non-passive for touchstart and touchmove, claim non-control edge touches immediately, preserve normal control taps, and prevent every move that begins inside the edge strip regardless of direction. Mount it once above all routes. `.app-content` is the vertical overscroll surface for every route, continues behind the floating glass bottom navigation, and must retain enough bottom padding/scroll padding to expose the final content above that navigation. The top header remains opaque white, and route content enters over 0.65 s with the established blur-to-sharp motion. Changing the month with the header arrows replaces that motion with a two-layer horizontal slide on the shared `--page-slide-motion` timing, which reuses the navigation-detail push curve and which both layers must read from so they cannot drift apart: the outgoing month slides off one edge while the incoming month slides in from the other, matched 1:1 so the two read as one moving surface. Forward months enter from the right and earlier months from the left. The outgoing layer is a static DOM snapshot cloned when the arrow is pressed, so it must stay visually frozen — every animation and transition inside it is suppressed — and it is clipped to the content area rather than crossing the desktop rail. A month change with no matching snapshot, including the month picker and browser history, keeps the blur-to-sharp entrance instead of sliding half of it. Settings and Organize suppress the entrance animation entirely for month changes, however the month was chosen, and every tab change keeps the blur-to-sharp motion.
- Every tab adds a touch pull-to-refresh at the top of `.app-content`, refetching the selected month's snapshot and announcing the outcome under that tab's own name. It does not fake the rubber band, and no script ever positions anything: `.app-content` keeps `overscroll-behavior-y: auto`, nothing calls `preventDefault`, and WebKit's own elastic bounce moves the content. Script-driven transforms read from `scrollTop` trail the compositor-driven bounce by a frame and visibly twitch, and a CSS scroll timeline cannot help because it clamps at zero and never sees overscroll. Content above the scroll origin is not painted in the overscroll gap either, because WebKit's scroll layer spans only the reachable scroll range, so the 58 px indicator band must live inside that range. `.app-content` therefore extends `--pull-band-height` up under the opaque header (negative top margin, matching top padding and `scroll-padding-top`), and the band is an absolutely positioned first child filling that padding. At rest the header covers it; the native bounce carries it out with the content, frame-exact, with no script involved. Anything sticky inside the scroller must add `--pull-band-height` to its `top` (the desktop `.right-rail` does), and the month-slide snapshot `.page-slide-out` repeats the same top padding so the outgoing page does not jump. `pull-gesture.ts` only observes: from the first touch or scroll event until the finger is up and the bounce has returned, it reads `max(0, -scrollTop)` every frame and writes `--pull-progress`, which drives the dial's opacity, scale, and arc fill. Browsers that never report a negative `scrollTop` (Android, desktop) therefore have no pull-to-refresh, by decision. Because WebKit only rubber-bands a container that actually overflows, coarse-pointer view roots inside `.app-content` are at least `100% + 1px` tall. The pull never starts while a sheet, a pushed detail, or a list drag is active. The arc starts filling at 29 px of overscroll (`pullFillStart`, half of `--pull-band-height`, where the dial clears the header; keep the two in step) and completes at the 115 px release threshold, and release past it refreshes; a shorter release just bounces back. The content is never held open while refreshing, because the web has no equivalent of UIRefreshControl's `contentInset`: WebKit's bounce always returns to zero, a negative `scrollTop` cannot be written, and every way tried of holding the content failed on device. Summing a CSS `translate` with the native bounce-back stutters however the curve is tuned. Swapping the bounce for a `translate` by zeroing `scrollTop` still jitters and flashes. Toggling the scroller's `overflow` makes WebKit rebuild the scroll layer, which flashes. Per-frame script compensation lags a frame and twitches. So on a refreshing release nothing touches the scroller and the content bounces back natively. Instead `markRelease` writes the release overscroll to `--pull-release` and enters the `releasing` state, which hides the in-scroller band and shows `.pull-refresh-float`, a 44 px white chip carrying the same dial, exactly where the band's dial was. The `refreshing` state then glides the chip on `--pull-hold-motion` to `--pull-float-top` below the header, where it floats over the content and spins. The chip's `z-index` keeps it above `.app-content` and below the header. At the end of a refresh the chip fades and shrinks on `--pull-settle-motion`; keep `settleDuration` in `pull-gesture.ts` equal to its duration, since it clears the state attribute once that transition ends. The spinner holds for at least 1,080 ms and at most 5 s, and the outcome is announced in a polite live region rather than a toast.

- The Better Buddy launcher is the 64 px robot icon (`src/components/assistant/better-buddy.png`, transparent, no backing disc) over a soft cornflower halo and a floor shadow, fixed against the left or right edge, and rendered in the app frame rather than inside `.app-content`, whose entrance animation transforms its children. On desktop a left-docked launcher clears the 190 px sidebar. A press that moves more than 8 px becomes a drag: the button follows the pointer with an inline transform and no transition, and on release it settles against the nearer side edge at the height it was dropped, animating from the drop point (FLIP) with the detail push curve. When a drag ends, a one-shot capture-phase listener swallows the next click anywhere in the page for 600 ms and the touch end is cancelled, because a browser synthesizes a click at the drop point that would otherwise activate the control beneath Better Buddy or reopen the chat. The halo and floor shadow are gradients on `BetterBuddyFigure` pseudo-elements, never a `drop-shadow` filter, which clips at the image box. The robot floats with a 3.6 s up-and-down loop while the floor shadow shrinks and fades in step, and on an independent 10 s cycle it rests, then turns around on its vertical axis twice (`rotate: y 720deg`, under a perspective of five figure widths) over the last 3.8 s. Every Better Buddy animation pauses while dragging. The launcher stays hidden until the browser is idle after hydration plus 600 ms, then flies in from its edge with a slight overshoot using the individual `translate` and `rotate` properties, which leaves `transform` free for dragging and the drop settle. The global reduced-motion rule reduces the float and the flight to their end states. The side and height are stored per browser as `betterBudgetAssistantPosition` (`side:fraction-of-viewport-height`), and CSS clamps the resting height below the header and above the mobile bottom navigation, so rotation and resizing never strand it. It sits above page content and the bottom navigation and below the sync indicator and sheets. Opening the chat sends Better Buddy running off his own screen edge (`buddy-leave`, 380 ms, a slight wind-up away from the edge first, fading only on the last frame), and he then slides into a 44 px seat beside the sheet title (`titleAdornment`) from beyond the chat's left edge, which the sheet's `overflow: hidden` clips, after a 380 ms delay, as the sheet settles, so he seems to have run over (`buddy-seat-in`, 720 ms: 400 ms to a small overshoot, then 320 ms easing upright on `cubic-bezier(0.45, 0, 0.35, 1)`). Closing the chat drops `data-away`, which swaps the launcher's animation back to `buddy-arrive`, so he flies back in from his edge as on launch, but after a 280 ms delay (`data-returning='after-sheet'`) so he comes back while the 0.6 s sheet exit is finishing rather than as the chat starts leaving. A drag dismissal reports the close only after its velocity-matched exit has carried the sheet off screen, so the sheet's `onDragDismissStart` fires on release, as that exit begins, and the launcher returns then with `data-returning='now'` and no delay, alongside the departing sheet. `data-away` is its own state rather than the sheet's `open`, so Better Buddy can come home before the sheet reports the close. The launch arrival (`buddy-arrive`) is 1.1 s: 648 ms to the overshoot, then 452 ms easing upright on the same gentle curve, set as the overshoot keyframe's own `animation-timing-function`, because the element-level curve applies to every keyframe segment and its fast start snapped him upright. Both are CSS animations on the individual `translate` and `rotate` properties of the launcher and the seat wrapper, never on `.buddy-figure-art`, so the float and spin keep running. This replaced a script-driven flight of a ghost copy between the launcher and the seat, which handed off between separately animated copies and on iOS Safari froze and jumped the spin when the freshly mounted seat was revealed mid-turn. Every copy's float, spin, and shadow still start at the document timeline's origin (`startTime = 0`), so the launcher and the seat share a pose. Reduced motion removes the seat's and the return's delays along with the durations. The chat itself uses the standard raised sheet titled Better Buddy, with no close button (`showClose={false}`; drag, overlay, and Escape still dismiss it), **New chat** as the header action once a conversation exists, a greeting and suggestions in its empty state, new messages animating in (the person's from the bottom right, Better Buddy's replies and the typing indicator from the bottom left, each a short rise, fade, and scale on a slight spring overshoot, using the individual `translate` and `scale` properties); messages already present when the sheet opens are recorded at mount by `TranscriptMessages` and never replay; reopening at the latest message (a stable ref callback on the end marker sets the sheet body's `scrollTop` when the sheet mounts, instantly rather than smoothly), and the composer in the sheet footer; closing the sheet returns focus to the launcher. Below 760 px an overlay tap, Escape, or any other non-drag close slides the chat out over 0.6 s on `cubic-bezier(0.45, 0, 0.25, 1)` with the overlay fading in step, instead of the shared 0.45 s sheet exit, whose curve starts at full speed and read as abrupt with no finger motion behind it; the rules key off the seat with `:has()` in `assistant.css`, and a drag dismissal still sets its own matched exit. The composer uses a 16 px font so iOS does not zoom on focus. Below 760 px, while the keyboard is down, the chat keeps the standard raised-sheet height, sized to its content up to `min(92dvh, 850px)`. When the composer gains focus, iOS Safari still scrolls the page up to reveal it, natively and deliberately left alone; `useKeyboardLayout` in `keyboard-layout.ts` fits the chat to the visible area while the keyboard is up. Measured on an iPhone: about 100 ms after focus, Safari fires one `visualViewport` resize and scroll with final values (no intermediate steps), scrolls the document by the keyboard's height (`scrollY` 403 on an 812 px screen) although `html` and `body` are `overflow: hidden`, and shrinks `window.innerHeight` along with the visual viewport while `documentElement.clientHeight` stays full height. Fixed elements stay positioned against the full-height layout viewport, so the bottom-anchored sheet is carried up onto the keyboard by Safari's own scroll. The hook therefore changes only the sheet's height: when the visual viewport is at least 100 px shorter than the tallest height seen since the chat opened (reset on orientation change; never compare against `innerHeight`), it sets `data-keyboard-open` (safe-area top padding and square corners; the corners switch instantly because `border-radius` is not in the transition, so they round again the moment the keyboard starts closing. Transitioning them was tried and dropped: the continuous-corners painter writes the radius it paints back as an inline `border-radius`, which pins a `border-radius` transition, and animating a registered custom property instead worked but was not wanted) and animates `height` from the resting height to the visual viewport's height, which puts the sheet's top at the top of the screen, and eases the thread to the latest message over the same duration (`glideToEnd`, a frame loop that closes the starting distance from the end on an ease-out cubic while re-reading the scroll range each frame, since the sheet shrinks at the same time; an instant jump read as abrupt, and a smooth scroll after the resize felt worse than one during it); on close it animates back to the resting height and clears the inline height. `glide` measures both ends because CSS cannot transition out of a content-sized height, and the motion is 520 ms on `cubic-bezier(0.32, 0.72, 0, 1)`. What reaches the screen is Safari's native page slide, which follows the keyboard and cannot be observed from script because the reported values are final at once, plus this height change; the sheet's top travels monotonically only when the two share a pace, so the duration and curve are tuned by feel on device. 320 ms on `cubic-bezier(0.38, 0.7, 0.125, 1)` started fast and left a slight bob at the top. Moving the sheet's `top` as well was tried twice and is wrong: measured after Safari's scroll, the start position lay far above the screen (the sheet's top animated down from -559 px while the keyboard rose), which read as the sheet bobbing against the keyboard, and a per-frame version made content visibly jump around. Inline styles go on the chat sheet only, never on `body`, nothing runs while the sheet is being dragged, the inline transition is removed after each change so it never overrides the sheet's drag-settle transition, and the behavior applies only below 760 px so resizing a desktop window never restyles the centered modal. Neither a stand-in focus field (which avoided the page scroll but changed native focus behavior) nor resetting the document scroll is used.
